# Architecture

For contributors and reviewers. For the format itself, see [SPEC.md](../SPEC.md).

## Code layout

```
src/skillbom/
  frontmatter.py   Small, strict YAML-frontmatter reader (stdlib only)
  model.py         Finds skills on disk, hashes files, builds Skill / Knowledge objects
  generate.py      Turns skills into a CycloneDX 1.6 document (pure function + dumps)
  check.py         Policy rules over a BOM (pure function over JSON)
  verify.py        Compares skills on disk with a BOM (pure function)
  cli.py           argparse front end, exit codes, BOM discovery
tests/
  test_skillbom.py           unittest suite, including CycloneDX schema validation
  fixtures/repo/skills/      two small skills sharing one knowledge file
examples/
  grcskills-v0.1.0.cdx.json  reference output, regenerated byte-for-byte in CI
```

## Data flow

```
                     ┌──────────── generate ────────────┐
 skills on disk ──► model.load_skills ──► generate.build_bom ──► skillbom.cdx.json
                                                                      │
                                         check.run(policy, today) ◄───┤
                                                                      │
 installed skills ──► model.load_skills ──► verify.compare ◄──────────┘
```

`generate`, `check` and `verify` share one reader (`model.py`), so the fingerprint computed when publishing is, by construction, the one computed when verifying. `check` and `verify` never re-read the publisher's files; they work from the BOM.

## Design decisions

| Decision | Why | Trade-off |
|---|---|---|
| **A CycloneDX profile, not a new format** | Existing SBOM tools, validators and procurement processes already read CycloneDX. Adoption costs nothing. | Some concepts (knowledge freshness, file roles) are carried as `skillbom:` properties rather than first-class fields. |
| **CycloneDX 1.6** | Widest validator and tooling support today; already has `declarations` and `formulation` for the planned evidence model. | Revisit 1.7 once tooling catches up. |
| **Python standard library only** | Nothing to audit in the supply chain of a supply-chain tool; runs anywhere Python does, including locked-down CI. | Hand-written frontmatter reader instead of PyYAML (see below). |
| **Own frontmatter reader** | Determinism: every value is a string and the accepted grammar is small and documented. PyYAML would coerce types (`0.1` → float, `no` → false) and accepts far more than we need. | Some valid YAML is rejected. Errors are explicit, never silent. |
| **Per-file hashes plus a folder hash** | The folder hash makes `verify` a single comparison; per-file hashes make the report useful ("SKILL.md changed") and show each file's role. | Larger BOMs (80 KB for 11 skills). |
| **Hash = SHA-256 over a sorted `sha256sum`-style manifest** | Anyone can reproduce it with `find`, `sort` and `sha256sum`; independent of where the skill is installed. | File modes and empty folders aren't covered (see threat model). |
| **Reject symlinks and ambiguous names** | Fail closed: a link can point outside the skill, and a newline in a name could forge a manifest line. | A skill using symlinks must be changed before it can be described. |
| **Knowledge identified by content hash** | The same pack shipped in several skills dedupes to one component; a changed pack gets a new identity. | Two packs with identical bytes but different meaning would merge (harmless: they are the same bytes). |
| **Deterministic output** | Reproducible BOMs can be regenerated and compared by anyone, which is itself a check. CI fails on a single differing byte. | No wall-clock timestamp by default; use `SOURCE_DATE_EPOCH`. |
| **No network access** | Predictable, offline, and no data leaves the machine. `verify` finds a local BOM rather than fetching one. | Users download the BOM themselves. |
| **Keyless signing outside the BOM** | GitHub artifact attestations (Sigstore) tie the BOM to a repository and workflow without anyone managing keys. | Verification today assumes GitHub; a portable `cosign` bundle is on the roadmap. |
| **No LLM anywhere** | The checker must be deterministic and explainable. | — |

## Threat model

### What SkillBOM is for
Detecting that the skills someone is running differ from what a publisher released, and making the contents of a release inspectable.

### Assumptions
- The publisher's release workflow and signing identity are not compromised.
- The user checks the BOM's signature before relying on it.
- SHA-256 is collision-resistant.

### What it detects

| Threat | Detected by |
|---|---|
| A file in an installed skill edited after release (e.g. an injected instruction in `SKILL.md`) | `verify`: `MODIFIED`, file listed under `changed` |
| A file added to an installed skill (e.g. a new script) | `verify`: listed under `added` |
| A file removed from an installed skill (e.g. a guardrail reference) | `verify`: listed under `removed` |
| A skill installed that the publisher never released | `verify`: `NOT-IN-BOM` |
| A tampered or substituted BOM | `gh attestation verify` fails |
| A BOM edited to hide a change (hashes altered) | Signature check fails; `check` flags malformed hashes |
| A symlink smuggling in content from elsewhere | `generate` and `verify` refuse to run |
| A release with unversioned, unlicensed or authorless skills | `check` |
| Knowledge older than the publisher's policy allows | `check` (warning by default) |

### What it does not detect

| Gap | Why | Mitigation |
|---|---|---|
| A malicious or wrong skill released by its genuine publisher | The BOM faithfully describes what was released | Review skills before installing; evals (profile 0.2) |
| A compromised release workflow or maintainer account | The attacker can sign a BOM for malicious content | Branch protection, required reviews, tag protection on the publisher's side |
| Wrong `as_of` dates | They are the publisher's claims | Treat as declarations, not facts |
| What a bundled script does | SkillBOM records that a script exists, not its behaviour | Read the script; prefer skills without scripts |
| Changes to file permissions (e.g. making a file executable) or empty folders | Only file paths and contents are hashed | Planned for a later hash method |
| Files matching the exclusion list (`.DS_Store`, `*.pyc`, `__pycache__/` …) | Excluded so normal OS and Python artefacts don't cause false alarms | Agents don't load these; a later version may report them separately |
| Changes made after `verify` runs | It's a point-in-time check | Run `verify` in CI or before each session |
| Line-ending conversion on checkout | Bytes differ, so it shows as drift (a false positive, not a miss) | Disable conversion for skill folders |

### Inputs treated as untrusted
`SKILL.md` frontmatter, reference files and BOMs are all treated as data. The tool never executes skill content, never follows links, and never writes anywhere except the `-o` path given by the user.

## Testing

- `tests/test_skillbom.py` covers the frontmatter reader, determinism, location-independence of hashes, exclusions, symlink and duplicate rejection, every `check` rule, every `verify` status, BOM discovery and CLI exit codes.
- When `cyclonedx-python-lib[json-validation]` is installed (as in CI), every generated BOM is validated against the official CycloneDX 1.6 schema.
- CI's `example` job regenerates [`examples/grcskills-v0.1.0.cdx.json`](../examples/grcskills-v0.1.0.cdx.json) from the public grcskills tag on a clean runner and fails on any difference, proving determinism across machines.

## Releases

Tag `vX.Y.Z` (maintainers only) → `release.yml`: run tests, confirm the tag matches `__version__`, build the wheel and sdist, regenerate and check the example BOM, sign all of them with `actions/attest`, publish a GitHub release. Check a downloaded artefact with:

```sh
gh attestation verify <file> --repo grcmana/skillbom
```
